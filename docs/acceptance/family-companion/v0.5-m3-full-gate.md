## Why it fails (by cause)
1. **Answer layer needs a model (approval needed).** 34 cases require exact clarification field codes (e.g. `room_number`,
   `conflict_resolution`) and 21 dispositions are CLARIFY-vs-answer judgements. The service has only a deterministic planner
   (lexical relevance ≥ 0.25 → ANSWER; relevant but unconfirmed/out-of-window → CLARIFY; else NO_REFERENCE) and never generates
   field codes, so those are NOT_RUN/FAIL. 4 assertion failures (023/045/057/058) are lexical ranking putting a non-gold memory
   first; thresholds were NOT tuned on the eval set (a stricter rule still had 2 wrong assertions).
2. **Ports not offered (recorded NOT_RUN, never simulated):** `extract_image_fields` ×4 (no vision route approved) and
   `import_older_notice` (no source-version lineage). Their candidates therefore stay absent → 5 final-state FAILs.
3. **Semantics differ from the fixture:** 069 cleanup is synchronous here (`CLEANUP_COMPLETE_SYNCHRONOUS` vs expected
   `PENDING_ORIGINAL_OPERATION`); 067/070/077 expect generation jumps (+2 on relearn/household delete) that a forget counter
   cannot produce.

## Harness rules (honesty notes)
- The harness is the client: session/account epoch, local use_memory/ephemeral flags, frozen-snapshot continuation, and
  mapping a refused request (403/404) to BLOCKED only when the viewer holds/held a grant.
- Fixture → real-ID map comes from receipts. Seeds load in sha256 order; expired/future seeds without bounds are loaded as a
  validity window; superseded seeds without a same-id successor are loaded then superseded through `memory.supersede`.
- Runtime fields `membership_revision` and `memory_generation` are reported relative to the post-load baseline plus the fixture's
  initial value; client-side fields (account, epoch, mode, snapshot, dispatch, late delivery) come from the harness client.
- Text behaviours (`GUESS_ROOM_NUMBER`, `ASK_ALREADY_CLEAR_DATE_AGAIN` …) cannot occur because no free text is generated; that is
  not evidence the model path is safe.

### (3) `20261023100000` reminder lease vs its live callers
The only live caller of `proactive.claim_due_reminders` is **catpaw-proactive v10**: pg_cron `catpaw-proactive-tick` POSTs
`/scheduler/tick` every minute (timeout 25 s) → `proactive/service.mjs` `tick()` → `pg-store.claimDue`. catpaw-api has no
`/scheduler/tick` route (it uses the proactive service only for chat tools) and its role has no EXECUTE; catpaw-tick v16 has no proactive code.
Analysis: the 30 s lease could expire while a live worker is still in `fire()` (model text + inserts), and a second tick would re-claim.
That never produced a second **send**: `fire()` (live v10 and new code alike) inserts `reminder_due` with dedupe key
`due:<task>:<scheduled_at>` under `unique(user_id, dedupe_key) … on conflict do nothing`; `finishOccurrence` is fenced on
`next_fire_at = scheduled_at`; APNs is driven by the event row's own push claim/lease, not by the occurrence. The real risks were repeated
model calls and a late failing worker releasing (deleting) the newer claim.
Fix (migration edited in place, it is not applied in prod):
- lease 30 s → **15 min**, above the longest possible tick (one Edge invocation: wall clock ≤ 400 s paid / 150 s free).
- `releaseOccurrence` is fenced on the worker's own `claimed_at` (= the `p_now` it claimed with), so a stale worker cannot release a newer claim.
  The function signature is unchanged; the live tick keeps working against it.
- Test `family-m1-pg.test.mjs` REM-01 (held at +400 s, re-claimable at +15 min) and REM-05 (stall → re-claim → stale release is a no-op →
  both workers insert → exactly one `reminder_due` → stale finish is a no-op).

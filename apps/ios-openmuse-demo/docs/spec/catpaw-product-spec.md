# Catpaw-m iOS 产品实施规格

版本：产品实施稿 0.5  
日期：2026 年 10 月 10 日  
用途：供产品、设计和工程实施 iOS 版本，覆盖现有功能复刻、个人助理和语音，并持续推进至真实 Agent 能力验收。本文的场景选择、阈值和排期均为建议，不代表用户已作决定或系统已经具备相应能力。

## 结论

现有功能复刻是用户明确要求的基础工作。用户已指定 iOS 版本。当前路线是在原图证据覆盖矩阵和实施 Plan 上建立独立可运行的 SwiftUI B0 基础复刻工程，完成真实本地导航、交互和持久化，再把个人助理与语音融合进去；整理规格后立即进入具备条件的原生编码，不以 D0 或文档作为交付终点。暂无原宿主代码不会阻塞这条路线；原宿主集成另行验收。

Catpaw-m 的首版个人助理应围绕一件持续交代的事，把“记住要求、继续准备、带着结果回来”做成完整闭环。推荐用“持续研究一个技术主题并准备内容草稿”作为可替换演示场景。研发交付和生活安排保留相同机制，首版不同时铺开三个行业化产品。

本轮新增语音交代、连续对话、成果朗读和口述改稿。语音复用原对话和成果，不扩大业务权限；设备真实朗读与模拟语音、待接入 ASR 分别标识。原音默认不在应用内持久保留，远程处理须单独说明。

首页采用助理工作简报：突出一份已经准备好的成果，下面放少量跟进事项。用户可以直接阅读和调整成果；需要外发、增加数据来源或扩大执行范围时，在具体动作处确认。基础工程复刻现有侧栏、对话、进度面板、文件阅读器和半屏表单，再供新增模块共用；不把这些入口做成占位，不建立独立日历系统或审批工作台。

分别验收 D0 交互探索、B0 独立基础复刻、R1 真实有限闭环；D1 保留为未来原宿主适配集成路线，不是 B0 或独立 R1 的前置条件。B0 本地能力要真实可用，远端动作按 fixture 标识，不能称为已嵌入原宿主。约一周仅是原 D0 范围假设，不包括新增 B0 工程、D1 集成或 R1 后台交付。只有真实持久化、调度、权限与执行回执通过验证后，才称为能在用户离开后继续工作的 MVP。

## 1 已知基础和待核实条件

### 已知基础

以下依据主任务已复核的 31 张宿主截图和本轮反馈，不追加未经验证的界面细节：

- 现有移动端主要承接被动 Agent 对话；项目现统一称 Catpaw-m。
- 宿主使用黑灰底、绿色状态，侧栏有云端与电脑切换、新任务、定时任务、专家、技能、项目。
- 已有对话、进度面板、文件阅读器、半屏表单、设置与权限界面。
- 首版方向是主动、有记忆、能执行、可信的长期个人助理。
- 上一版的问题包括卡片堆叠、审批后台感、抽象文案。
- 独立 Swift 日历 Demo 已被否定；会前准备不是已选定的主场景。
- 用户已明确要求复刻现有功能作为基础；范围包含基础功能工程，不止保留导航。
- 原图 L0291 可见语音入口，但静态入口不证明连续对话、ASR、打断或后台能力已经存在。

### 不得先行承诺的能力

- 云端在应用关闭后持续执行的能力及可靠性。
- 长期记忆存储、跨任务检索、跨端同步、离线执行。
- 已连接的邮箱、日历、代码仓库、消息或发布平台。
- 现有任务系统是否支持父子任务、幂等执行、服务端调度和通知回执。
- 多设备状态一致性、数据删除的物理完成时限。

这些是工程接入核查项。未确认前，可在演示环境模拟，但必须明确标识，不能以成功状态包装尚未发生的外部动作。

## 2 定位和首版边界

### 核心用户任务

“我已经交代过这件事。你要记住关键要求，继续做能做的准备，有值得我看的结果再找我。”

优先支持正在做内容研究、研发交付或具体生活安排的用户。共同特点是：目标可以描述，资料范围可以界定，工作跨越不止一次对话，期间会产生可检查的中间成果。

### 首版承诺

在用户明确交代的范围、时段和权限内：

1. 保存当前事情的目标、要求和停止条件。
2. 在真实可用的触发条件下继续准备，遇到依赖时说明卡在哪里。
3. 产出可阅读、可修改、能追溯依据的成果。
4. 只在新结果、重要变化或必要决定出现时联系用户。
5. 用户随时能看清它在做什么、暂停它、改要求或结束它。

### 不作出的承诺

不把“有记忆”解释为自动读取所有历史，不把“主动”解释为持续制造通知，不把“能执行”解释为默认获得外发、购买、修改仓库或控制电脑的权限。未获验证的在线状态不能写成“我一直在跟进”。

## 3 推荐演示场景

### 首选建议 内容研究到可审阅草稿

示例委托仅用于演示：

“这周帮我跟进一个 AI 技术主题。先看我给的资料，补充可靠的一手来源，整理有哪些新变化，写一份适合给开发者看的短内容草稿。有会改变结论的新信息再告诉我，发布前问我。”

具体主题可以替换，不能默认为用户选择了某个模型、产品、视频方向或发布渠道。演示使用标注来源和日期的公开材料或固定测试资料，不需要真实外发。

首个可见成果包含：

- 一份完整短稿，而非只有“已找到 8 条资料”的统计。
- 2 至 3 个主要结论及对应来源。
- 本次更新和上一个版本的区别。
- 尚未证实的关键点，用普通文字说明。
- 一条具体后续动作，例如“按这个方向继续查证”或“把第二段改得更直接”。

### 选型理由

这个场景能同时验证持续委托、任务内记忆、来源检查、成果版本、主动回访和外发边界。阅读、提炼、私有成稿可以先完成，不必依赖邮件、日历、代码执行、付款或跨端控制。它也更容易让用户直接判断成果是否有用。

### 可替换场景

- 研发交付跟进：围绕一个明确仓库或 PR，整理失败检查和变更，准备修复建议；读取仓库、改代码、提交、合并是不同能力与权限。适合第二个接入验证，不把“检查通过”冒充“已交付”。
- 生活安排准备：围绕一项明确的周末安排，准备候选地点、交通和预约信息；先产出可用方案，再进入预订授权。适合验证时间变化，但容易引入定位、价格、商家与交易依赖。

三者共用底层模型，首演只填一个场景。会前准备可以未来替换，当前不设为核心入口。

## 4 产品结构和宿主关系

### 新增的最小界面

1. 助理工作简报：呈现最新重要成果和少量持续跟进事项。
2. 一件事的详情：目标、成果、下次动作、来源和简短记录。
3. 上下文中的二级面板：查看或修改这件事的要求、记忆、授权及通知。

B0 先复刻统一的对话、文件阅读器、进度面板和半屏表单；新增助理的结果阅读、继续交流、执行进度与确认复用这套真实本地组件与数据。未来 D1 回接原宿主时，再替换为经验证的宿主组件或桥接。长稿阅读和长文本修改使用全屏，不能为了统一形式塞入半屏。

建议在既有侧栏增加或承载“助理”入口，不改变云端与电脑切换的含义，不新增全局底部导航。具体插入位置交互稿需对照真实侧栏密度决定。首次进入不能强制接管用户正在进行的对话。

### 工作简报的内容顺序

1. 一个最值得看的结果：具体标题、1 至 3 行摘要、准备时间和来源截至时间、主要动作“查看草稿”。
2. 与该成果直接相关的下一步：例如“我会继续核实第二个结论”，或“发出前需要确认收件人”。
3. 轻量列表“还在跟进”：每行一个事情名称、一句当前状态、必要时一个明确阻塞原因。
4. 次要入口“交代一件事”，沿用现有输入方式。

不要把记忆数量、授权数量、运行次数、连接状态和待办数量同时放在首屏。无需要用户介入的情况时，不显示空的审批区。绿色只辅助表达状态，所有状态必须有文字。

### 主成果排序

先排可能影响明确截止时间的结果或决定，再排有实质变化且未读的成果，再排新准备好的普通成果。已读但仍有待处理问题可以保留；仅仅“运行了一次”不抢占主位。其他成果仍可从列表到达。

多个重要事件同时发生时，以一段简短汇总和列表承接，不生成一组等权重的大卡片。

## 5 概念与现有功能的关系

### 持续委托

持续委托是“一件需要继续负责的事”。它至少包含目标、资料范围、输出、可执行动作、触发方式和停止条件。它可以产生多次运行和多个成果版本，但用户仍在同一件事里继续交代。

内部最小字段：

- 委托 ID、所属项目和原对话 ID。
- 用户原始交代与当前目标。
- 资料范围、排除范围、执行环境。
- 本次要求、允许引用的长期偏好。
- 触发方式、下次预计检查时间或等待事件。
- 停止条件、可选截止时间、生命周期状态。
- 权限版本、通知偏好、最后检查时间。
- 最新成果和最新有效执行回执。

### 单次任务

解决一次请求，完成后不自动成为长期关注。“帮我了解一下”不能被解释为持续监控。“继续帮我盯着，直到……”才提供持续意图。可以从现有任务结果轻量选择“继续跟进”，保留原上下文。

### 定时任务

定时任务描述“何时触发”，持续委托描述“为何做、做到什么为止”。一个持续委托可以引用一个定时触发器；定时任务列表应展示所属事情，避免用户看到两份同名、可以互相矛盾的配置。关闭所属委托必须停止它的后续触发，不能留下孤立定时器。

### 专家与技能

专家提供特定领域的处理方式，技能提供完成某步骤的方法。它们参与一件事的运行，不独立成为另一个人格或单独的审批队列。使用专家、技能不会自动扩大数据访问或执行权限。

### 项目

项目是事情和资料的归属空间。项目内要求可以被选择性复用，但不自动变成全局用户偏好，也不自动允许访问其他项目。一个成果在项目和助理入口出现时，应引用同一记录，不能复制后各自更新。

## 6 首次委托到主动回访的用户旅程

### 6.1 从原对话开始

用户在原有输入区交代一件事。系统先判断是否明确需要持续跟进。

- 单次意图：照原任务处理，结果后可轻量提供“继续跟进”。
- 明确持续意图：生成简短的工作约定并开始已获授权的准备。
- 目标不明、范围可能扩张或缺少不可替代条件：只问影响下一步的一个问题；独立、低风险的准备可以继续。

不要要求用户先完成一套“助理人格、记忆、通知、权限”初始化问卷。

### 6.2 确认理解而非重复审批

回复示例：

“我会围绕你给的主题整理资料和更新草稿，保留来源；有影响结论的新信息再找你。发布前会让你确认。这件事先跟进到本周结束，你可以随时改。”

仅当用户原话已经给出了本周时段时，才能把“本周结束”作为约定；未指定时段可显示建议并提供修改，不能静默创建无期限高频工作。明确持续请求已足以创建其范围内的委托，不再要求点击“确认授权”才能开始阅读。

首次最多显露三个可改字段：要交付什么、跟进到何时、什么情况下通知。执行权限和资料范围在用户相关的情境中展开。

### 6.3 首次准备

对话和进度面板展示具体动作，例如“核对原文”“整理差异”“形成第一版草稿”。如果只是排队，写“等待开始”；如果电脑未连接，写“等待电脑连接”。没有可靠遥测时，不显示伪精确百分比或滚动假日志。

### 6.4 用户离开

云端执行已验证时，显示“已在云端继续准备”。依赖用户电脑时显示“需电脑保持连接”；纯交互演示显示“演示流程”。执行环境来自实际任务归属，不能随用户在侧栏切换视图而自动迁移任务。

### 6.5 有成果回来

工作简报展示“技术主题草稿已准备好”，带一段真正可用的摘要。通知只在满足约定阈值且系统有可用通知能力时发送。通知点击直接打开对应版本或其最新替代版本，并解释更新关系。

### 6.6 阅读和修改

“查看草稿”直接进入阅读器。用户提出“第二段短一些”，产生同一成果的新版本，旧版可查看。此项修改默认只影响当前稿件；不能凭一句修改自动建立全局写作偏好。

### 6.7 需要外发

只有用户明确提出发送或委托中有覆盖本次动作的长期授权，才进入外发流程。缺收件人则先补齐，不默认最近联系人。确认面板紧贴将发出的稿件，显示渠道、接收者、完整内容、附件、可见范围和真正的“发送”动作。

首演可演示确认和回执状态，但若未接入真实发送，按钮必须写“模拟发送”，结果必须写“模拟回执”。

### 6.8 后续变化和结束

有新证据但不改变结论：静默更新来源记录。实质改变已交付结论：生成带差异说明的新版本，联系用户并指出影响。达到停止条件：结束后续检查，保留成果；用户仍可重新交代，但这会形成新的有效目标和授权检查。

## 7 状态模型与转移规则

用独立状态避免把“有成果”“有通知”“等待批准”“整件事结束”混为一谈。内部枚举无需全部展示给用户。

### 7.1 委托生命周期

产品与技术稿共用以下 API 状态，前端只做简明展示，不创建第二套业务枚举。

| API 状态 | 用户可见文案 | 进入条件 | 可转向 |
| --- | --- | --- | --- |
| draft | 还需要补充一项信息 | 持续意图存在，关键目标或边界不全 | active；弃置记录 discarded_at |
| active | 正在跟进 | 约定成立，尚未达到停止条件 | paused、completed、cancelled、expired |
| paused | 已暂停 | 服务端确认暂停已生效 | active、completed、cancelled、expired |
| completed | 已结束跟进 · 目标已完成 | 达到用户明示的完成条件 | 新建后续委托 |
| cancelled | 已结束跟进 · 你已结束 | 用户结束委托 | 新建后续委托 |
| expired | 已结束跟进 · 约定时段已结束 | 有效时段到期 | 新建后续委托 |

“已结束”是 completed、cancelled、expired 的共同显示，不是另一个 API 状态。归档仅为终态记录的 archived_at 可见性字段；取消归档只恢复展示，不能恢复 active 或触发检查。草稿弃置仅记录 discarded_at，不开启任何调度。

“等待资料”“等待确认”“等待电脑”属于运行阻塞或健康状态，不把委托自动结束。结束不自动删除成果。客户端点击暂停但尚未得到服务端确认时，显示“正在暂停”或“暂停待同步”，不能提前显示“已停止云端”。

### 7.2 一次运行

| API 状态 | 用户可见文案 | 关键语义 |
| --- | --- | --- |
| queued | 等待开始 | 资源可用后 preparing |
| preparing | 正在准备 | 整理范围、来源和上下文，随后 running |
| running | 正在核对资料等具体动作 | 进入 verifying、等待或故障分支 |
| verifying | 正在核实结果 | 有证据后 succeeded；无法判定时 outcome_unknown |
| waiting_approval | 等待你确认这项动作 | 成果仍可阅读；批准有效才继续相关步骤 |
| waiting_dependency | 等待资料／连接／电脑 | 依赖恢复且委托有效后重新评估 |
| retry_scheduled | 稍后重试 | 仅对已知可安全重试的步骤使用 |
| cancel_requested | 正在停止 | 不能表示外部动作已撤回 |
| cancelled | 这次已停止 | 停止执行，已有外部动作仍按回执核实 |
| succeeded | 本次准备完成 | 可产生新成果；委托仍可 active |
| failed | 这次没有完成 | 原因和已完成部分仍可查看 |
| outcome_unknown | 结果待核实 | 先查回执；不可直接重复外部动作 |

等待状态必须有 blocking_reason：缺输入、待动作确认、权限失效、执行环境不可用、外部依赖未就绪、来源不可访问。前端展示具体原因和下一步，不只显示“异常”。已有适用成果时，no_change 可作为成功运行的结果，不凭空生成新版或通知；首次委托还没有成果，即使命中公共来源缓存，也应准备符合本次要求的首版稿件。

### 7.3 成果状态与已读记录

- draft：尚未形成可交付版本。
- ready：已形成可审阅稿件，显示“已准备”，未必经过用户查看。
- superseded：被新版本替代，旧版保留明确标识。
- stale：关键来源过期或新证据使其不宜继续使用。
- withdrawn：发现严重错误或权限问题，默认不推荐继续使用，保留必要说明。

已读通过每个用户、每个成果版本的独立 view receipt 记录，不写入上述状态。收到推送不等于已查看；ready 可以同时是已读或未读。最终稿已读不等于停止持续委托，也不等于同意外发。

### 7.4 授权状态与执行阶段

Approval 状态使用 pending、approved、rejected、expired、invalidated、consumed、revoked。批准绑定具体 ActionEnvelope 和内容版本，不能只记录一个笼统 approved=true。批准与执行回执分开保存。

有外部副作用的动作按以下执行阶段显示：

| 执行阶段 | 用户可见含义 | 取消保证 |
| --- | --- | --- |
| not_started | 尚未开始 | 服务端撤销生效后保证阻断 |
| reserved | 已安排，尚未提交执行 | claim 只是预约，仍在保证阻断范围 |
| dispatch_committed | 已进入执行阶段，结果待核实 | 服务端 dispatch_commit 已提交，不再保证取消；不代表已发出网络请求 |
| accepted | 对方已接收，等待核验 | 不等于已完成，不能承诺撤回 |
| verified | 已核验完成 | 展示证据或目标链接 |
| failed_definite | 已确认没有完成 | 仅在证据支持安全重试时可重试 |
| unknown | 结果待核实 | 核对实际结果，不自动重发 |
| cancelled_before_dispatch | 已在进入执行前阻止 | 有服务端阻断记录 |
| cancelled_before_transport | 已确认未发出并停止 | 仅在提交执行后仍可证明未传输且已阻止时使用，不能作为默认保证 |

服务端 dispatch_commit 是唯一取消保证边界。用户点击、worker claim、请求进入队列、供应商接收都不能替代这个边界。暂停或撤销事务先于 dispatch_commit 生效时必须阻断；dispatch_commit 先发生时，只能说明“可能已发生，正在核实”，即使当时尚未取得供应商回执。

### 7.5 展示状态优先级

会影响用户已采取行动的错误或时限风险优先；其次是需要用户决定；其次是新成果；最后才是常规运行。异常和结果可以同时存在，例如“草稿可阅读；外发失败”，不能用红色错误页面盖住已经完成的准备。

## 8 交付阶段与功能优先级

阶段名称与技术稿一致。D0、B0、D1、R1 是不同证据门槛，不是必须串行的上线步骤；D1 原宿主集成可选。不能用 D0 演示截图替代 B0 本地功能验收，也不能用 B0 的 fixture 成功替代 R1 真实后端验收。

### D0 宿主对齐交互原型

设计探索层。对照真实宿主图验证交互语言，可在独立原型环境运行；后台运行、通知和外发状态用明确标识的 fixtures 模拟。它支持 B0 设计，但不能代替用户要求的基础功能工程。

- 模拟从原对话交代持续事情，查看和修改工作约定。
- 助理工作简报：一个主成果、少量跟进行、真实空态。
- 同一事情的目标、准备过程、成果、来源与模拟对话衔接。
- 草稿直接打开、修改形成新版本、比较本次变化。
- 显式任务要求的保存、修改和删除演示。
- 上下文中的执行边界、具体外发确认与撤销演示。
- 暂停、恢复、结束，以及待输入、待权限、离线、失败、结果未知等关键状态。
- 演示数据隔离、重置、时间推进和“模拟”标识，避免测试产生真实外发。
- 语音交代、连续对话、转写编辑、朗读、口述改稿和异常状态演示；可验证设备 TTS 时单独标为真实朗读，ASR 未接入则明确模拟。

D0 只能证明设计与可点击流程，不证明现有侧栏路由、原会话 ID、宿主阅读器或权限组件已经接通。

### B0 独立基础复刻

当前新增的基础交付，实施为 SwiftUI 原生 iOS 工程。依据 31 张原图证据矩阵重建现有已证实功能，工程可独立运行，不依赖原宿主代码或桥接。界面、导航、本地操作与持久化必须真实；需要远端的动作使用明确 fixture，后续按适配器替换。

- 完成云端/电脑视图、项目归属、新会话与历史、任务进度、文件树及阅读器的本地主链。
- 补齐定时任务、专家、技能、设置和已证实输入面板，不能只留入口占位。
- 建立同一套实体 ID、状态和本地持久层，新增助理和语音复用，不形成相互隔离的演示。
- 每个字段和行为标 confirmed、inferred 或 unverified，截图未见不臆造原有功能。
- 按第 21 节 L1 至 L5 和 BF01 至 BF20 验收，区分真实本地、fixture 远端和已接通的真实能力。

B0 可交付真实设备 TTS 等独立能力，但不能以此宣称 ASR、云调度或原宿主连接已经完成。缺少原宿主源码不是 B0 的阻塞项。

### D1 原宿主适配集成

未来可选路线，依赖原宿主工程代码或可用桥接。在原宿主中接入已完成的入口、身份、路由与组件，后台仍可使用明确标识的 fixtures；这项依赖不阻塞 B0，也不阻塞独立工程接 R1 后端。

- 现有侧栏、云端与电脑切换、返回和关闭路径真实有效。
- 原对话 ID、成果 ID 与对应详情传递正确。
- 阅读器、进度面板和半屏表单按宿主实际组件接入。
- 模拟数据与用户真实任务隔离，不伪装真实持续执行。
- 真实宿主音频入口、系统 TTS、音频中断、前后台和权限拒绝测试；不把模拟转写称为真实 ASR。

证据必须来自真实宿主构建和实际操作，独立原型无论多像宿主都不能替代 D1。

### R1 真实有限闭环

一个实际内容研究委托与私有草稿，不要求真实外发。可在 B0 独立工程上接入，依赖经过验证的身份与权限、服务环境、存储、模型和来源读取能力，不要求先取得原宿主源码。

- 委托、成果、范围与状态持久化，应用与服务重启后可恢复。
- 至少一种可靠执行环境和一种真实触发方式；跨不同日期完成至少两次持久运行。
- 真实来源读取、变化核对、来源更新时间与无变化结果记录。
- 执行前授权校验、版本检查、重复动作防护和回执核实。
- 服务端暂停、结束、撤销实际生效；对 dispatch_commit 之后的动作核实而不假称取消。
- 至少一种可验证的返回用户方式；未实现系统推送时只能承诺应用内更新。
- 任务内记忆删除与停止使用可验证，覆盖排队和在飞上下文。
- 语音范围另验证一个已选定并说明处理边界的 ASR 路线；TTS 可优先采用设备能力，不把自托管模型当作后台研究闭环依赖。

自然来源没有更新时可用标明的测试注入验证变化路径，但必须分别报告“调度真实运行”和“来源变化为测试注入”。

### R2 多委托与记忆扩展

第二个研究场景、更多来源、项目作用域、显式跨任务偏好、冲突解决、通知偏好与成本控制。以 R1 稳定为前提。

### R3 账号连接与外部写操作

逐个加入低风险外发或外部修改适配器，每个完成目标核实、最小权限、不可变批准、dispatch_commit、幂等、unknown 对账和回执验收。D0 展示过确认界面不表示真实外发已实现。

### R4 电脑与复杂执行

在明确需求下接入电脑、文件和本地应用；验证环境身份、在线状态、范围权限和执行后结果。复杂多人协作、全量跨端接力、专家技能市场和高风险自动执行不作为本轮依赖。

## 9 持续执行与触发策略

### 触发类型

- 用户继续交代：立即运行相关步骤。
- 已授权来源发生变化：可用时优先事件触发。
- 到约定检查时间：没有事件能力时进行低频检查。
- 前置条件恢复：先检查委托是否仍有效、授权是否仍有效，再恢复。

### 范围和停止

每件持续事情必须有清晰停止语义：到某日、到某结果、用户结束，三者至少一项明确。用户明确要求长期跟进时可以持续，但要展示如何暂停和结束；不从单次任务推导无期限监控。

不得为了“主动”自行扩大主题、增加私人来源、联系第三方或切换执行环境。需要扩大范围时解释收益和代价，得到授权后再继续相关部分。

### 检查频率建议

内容研究首演建议每日最多一次常规检查；有用户指定时间或已订阅的可靠事件则按约定触发。这只是产品默认建议，不代表任何任务已经建立调度。实际频率应受来源更新速度、截止时间、执行成本和用户要求约束。

不把“每日检查”与“每日通知”捆绑。没有新的有效结果时，可以成功检查但不通知。

## 10 触达与静默策略

### 四类输出

1. 静默记录：重复资料、轻微来源更新、未改变结果的常规检查。仅写入详情。
2. 应用内更新：新成果已准备，尚不急；工作简报在用户打开时展示。
3. 普通通知：存在有用新成果、用户等待的结果或需要决定的下一步，且有明确通知许可。
4. 紧急提醒：只用于该委托中明确时限或高后果变化；普通技术资料更新不能升级为紧急。

### 建议默认值

这些数值用于首轮验证，可配置，不是已验证的用户偏好：

- 同一委托同一成果版本最多一次主动通知。
- 多件非紧急更新合并；首版默认每日最多一条非紧急汇总通知。
- 相同阻塞不重复催促。新时限或后果出现时才补充一次有新信息的提醒。
- 用户正在查看该成果或在相关对话中时，不再发同义推送。
- 用户忽略一条普通通知后，不以另一渠道追发。
- 采用设备有效时区和可编辑的安静时段。未知时区时不根据猜测安排夜间推送；只保留应用内更新。

可供演示的安静时段默认示例为 22:00 至 08:00，但需明确可修改，不能冒充从用户行为推断出的习惯。操作系统通知关闭时，写“下次打开可看到结果”，不要表示用户一定会收到。

### 请求确认

确认属于具体动作流程，不单独增加通知噪声。能先完成的准备继续完成，再一次性提出必要问题；若确认过期或用户拒绝，保留成果，并明确仍可做什么。拒绝外发不应停止阅读、改稿等已授权工作。

## 11 记忆来源与控制

### 首版先分清三类信息

1. 任务要求：用户为这件事明确说过的目标、约束、时间和偏好。D0 展示，R1 实现。
2. 可复用偏好：用户明确要求“以后也这样”或在界面选择长期记住。可作为 R2；没有真实持久化和作用域控制时，不宣传为已实现。
3. 当前推测：从操作或资料推断出的临时判断。只能作为有来源、可纠正的工作假设，不自动写入跨任务记忆。

演示需要体现“有记忆”时，优先展示“本次沿用你对这件事的三个要求”，不要展示“我已经了解你”的笼统宣言。

### 每条可用记忆应有的信息

内容、来源位置、创建和最后更新时间、作用域、是否用户明确表达、当前有效性。来源能够回到具体对话或用户指定资料；不能只写“AI 学习得到”。机密、账号凭据与认证令牌不得作为普通记忆存入。

### 作用范围

默认为当前委托。用户明确选择后才可扩大到同一项目或全部助理任务。项目内信息不能被其他项目自动使用。资料中出现某人的联系方式不等于用户允许今后联系此人。

### 界面行为

在结果详情显示“这次按这些要求准备”，点击展开 2 至 4 条具体要求。每条可以修改、仅本次不使用、删除。把“记住我的习惯”和“允许替我发送”分开，前者不能产生执行权限。

### 修改、删除与冲突

- 修改在服务端确认保存后影响后续生成；本地未同步时明确标记。已交付成果保持原版，并提示是否按新要求重做。
- 删除在服务端确认生效后立即阻止新任务读取该记忆，取消或重算依赖它的准备步骤；已经在飞的生成在发布成果前还要核对删除版本。外部动作能否阻止以 dispatch_commit 为边界，不能声称记忆删除可撤回已进入执行阶段的传输。删除需要传播到索引、摘要、缓存和排队任务上下文；不能只删除主记录后继续从副本使用。
- 删除记忆不会撤回已发出的消息，也不自动删除源对话或既有成果；界面需说清。
- 源对话仍在时，系统不得立刻从同一句话重新提取已删除记忆。需要删除抑制或等价机制，直到用户重新明确提出。
- 源信息与新指令冲突时，以用户最新明确指令为当前任务依据；涉及重要结果时显示冲突而不是静默覆盖。
- 时间性事实必须有适用期。过期后不当作当前事实使用。
- 不承诺未验证的物理删除时限；可验证的是即时停止使用、后续检索不命中，以及按实际存储机制完成删除。

## 12 权限、确认与执行回执

### 权限分层

- 资料读取：限定连接器、资料集合、项目和时间范围。
- 私有准备：分析、生成、保存到已授权的私有工作区。
- 修改外部状态：修改文件、任务、仓库或日历，按具体操作判断。
- 对外表达：发送、发布、邀请、提交，核对接收者、内容和范围。
- 高风险动作：支付、凭据、永久删除、账号安全等，不作为首版自动执行内容，沿用平台已有政策和强确认或交接流程。

下表是首版产品行为，不取代平台更严格的权限政策：

| 动作 | 首版行为 |
| --- | --- |
| 打开已经准备的私有草稿 | 直接打开，不审批 |
| 在当前授权范围内核对来源、重写私有稿件 | 继续执行；不重复询问相同权限 |
| 新增私有数据来源或新连接器 | 说明来源和用途，完成对应授权后再读取 |
| 把当前要求记到其他项目或全局 | 用户明确选择作用域；不能静默扩张 |
| 向明确接收者发送或发布 | 有覆盖本次内容和目的的明确授权才执行；否则按动作请求确认 |
| 改收件人、加附件、变更可见范围、实质改变已批准正文 | 旧批准失效，显示变化并重新获得必要授权 |
| 安全敏感或高后果操作 | 交由现有严格权限机制；不得用“长期助理”总开关绕过 |

### 确认面板必备字段

动作、目的、真实接收者或目标资源、将使用或发送的数据、完整内容和附件、有效期、可撤销范围。按钮写真实动作，如“发送给该收件人”；不能用含糊的“继续”掩盖外发。

默认一次批准只覆盖该动作。要设置长期授权，必须明确动作类型、对象范围、数据边界和期限，并有独立撤销入口。首版演示可以省略创建长期外发授权，避免把复杂授权管理当作核心体验。

### 授权与执行之间的竞态

点击确认后，网关在服务端 dispatch_commit 事务中原子核对当前内容版本、接收者、权限版本、委托状态、有效期和取消版本。worker claim 或 reserved 仅表示预约，不消费取消保证。服务端已生效的暂停、撤销或范围修改若先于 dispatch_commit，必须阻断旧动作；dispatch_commit 若先提交，界面即进入“可能已发生，正在核实”，不能等供应商接收后才承认存在风险。commit 本身也不能被描述为网络请求已经发出。

暂停或撤销后可以在仍有效的读取权限内核对既有动作结果，这不允许开始新的写动作。补偿、删除已发内容或撤回需要适用的单独授权与回执。

### 执行回执

“已发送”“已更新”“已完成”必须对应可核实的外部回执、目标链接或验证结果。进入队列或 reserved 只能显示“已安排，尚未提交执行”；dispatch_committed 显示“已进入执行阶段，结果待核实”；accepted 显示“对方已接收，等待核验”。没有执行后证据不能显示完成。超时但可能已完成进入 unknown，禁止直接重新发送。

## 13 暂停、撤销、恢复、重复与离线

### 暂停和结束

- 暂停在服务端确认生效后停止新调度；其事务先于 dispatch_commit 时保证阻断尚未进入执行阶段的动作。commit 后不再保证取消，继续在有效读取权限内核实已有动作，并说明可能已经发生。
- 结束在服务端确认后停止此委托的后续检查和关联触发器，保留可阅读成果和必要记录；已越过 dispatch_commit 的动作仍按实际回执处理。
- 撤销某项权限只阻止依赖该权限的步骤，不删除整个事情。
- “稍后提醒”只改变触达时间，不等于批准，也不等于结束。

### 恢复

用户恢复时先展示停顿期间的重要变化，并重新验证权限、资料可用性、目标时限和成果是否过时。不能一口气补执行所有错过的定时动作。常规资料检查最多合并成一次当前检查；外发不会因恢复而批量补发。

### 重复执行和重试

每个有外部副作用的动作有稳定动作 ID 和内容指纹。同一次确认、重复点击、网络重传、应用重启不能产生两次相同外发。可重复的读取或私有生成可安全重试；外部状态未知时必须先查询或人工核实，不能把“再试一次”作为通用按钮。

### 离线与跨环境

- 移动端离线：显示缓存内容与最后更新时间；本地草稿可编辑并标记待同步。暂停或撤销只能记录待同步意图，不能提前显示云端已停止。审批和外发不排队自动提交，重连后必须读取当前动作并由用户重新确认。
- 云端可运行且已验证：移动端离线不代表后台暂停。
- 电脑依赖离线：只暂停依赖电脑的步骤；独立云端准备仍可继续，但不得静默把文件或权限迁往云端。
- 电脑重新连接：检查委托和授权仍有效后恢复。
- 多端同时修改：以版本检查避免静默覆盖。若多端同步尚未实现，首版只在已支持端范围内承诺状态一致。

### 其他异常

- 来源打不开：保留已完成部分，明确缺失来源和对结论的影响；不伪造引用。
- 一半完成：可以交付可用部分，指出未完成内容，不能把整件事写成失败或全部完成。
- 推送失败：成果仍保留在应用内；同一通知不无限重发。
- 登录过期：阻止相关读取和执行，指向现有重新连接流程；不请求用户在聊天中提供密码。
- 用户删除委托：必须说明是否只删记录、是否一并删除成果，以及实际可恢复性；不把归档包装成彻底删除。

## 14 可直接实现的文案示例

以下均为演示用文案，数量和内容需要与实际数据一致。

- 空态：“有件事想让我继续准备吗？” 次文案：“从一份资料研究或一项待交付的工作开始。” 主动作：“交代一件事”。
- 主成果：“技术主题草稿已准备好”。摘要：“整理了两处关键变化，并把还没证实的部分单独标出来。” 主动作：“查看草稿”。
- 跟进行：“内容研究 · 下一次检查在明天；有重要变化再告诉你。”
- 任务要求：“这次沿用：面向开发者、保留原始来源、发布前确认。”
- 等待来源：“有一份资料暂时打不开。其他内容已整理好，你可以先看。”
- 等待电脑：“这一步需要你的电脑连接。草稿已保留，连接后会先检查是否仍需要继续。”
- 已暂停，且无越过提交边界的动作：“已暂停后续检查。已经准备好的内容还在。”
- 暂停时已有动作越过提交边界：“已停止后续动作；这一项可能已经发生，正在核实。”
- 离线暂停：“暂停请求还没同步，云端可能仍在继续。”
- 内容更新导致批准失效：“正文在你确认后有修改。请看这一版，再决定是否发送。”
- 发送结果未知：“这项动作已进入执行阶段，但还没查到结果。我会先核实，避免重复发送。”
- 权限撤销：“已停止使用这个来源；已有稿件可能仍含引用，可以查看并移除。”

避免使用“行动中枢”“智能洞察”“信任值”“唤醒潜能”等难以说明真实工作状态的标题。

## 15 可执行验收标准

阶段标注规则：D0 用 fixtures 验证交互设计；B0 验证独立复刻工程的真实本地路由、交互和持久化，以及边界清楚的远端 fixture；D1 验证未来原宿主适配集成；R1 用真实服务验证持续研究与私有成果。外发、撤销竞态与供应商回执在 D0/D1 只能模拟，真实外部写操作须到 R3 逐适配器验收；不能用模拟通过声称后台通过。下列未单列阶段的交互用例可先在 D0 演示，涉及后台效果的保证必须在 R1 或 R3 实测。

### 核心闭环

- AC01：D0 模拟持续请求；B0 在独立工程真实会话中建立可查看目标、范围、停止条件的本地委托；D1 如回接原宿主再核对原会话，R1 核对服务端持久记录与无重复定时器。
- AC02：输入普通单次请求，不自动建立持续监控或系统通知。
- AC03：首次只缺一个必要条件时，只追问该条件；能独立执行的准备步骤不被无关授权阻塞。
- AC04：工作简报初屏只有一个主要成果动作；首屏能看懂准备了什么，不靠点开所有卡片理解。
- AC05：点击“查看草稿”直接看到完整成果，不出现授权弹窗。
- AC06：成果至少含实际正文、来源、更新时间及未证实项；无来源时明确标注，而非显示虚构链接。
- AC07：D0 模拟从成果返回对应对话并保留版本；B0 核对独立工程真实本地会话 ID 与版本，D1 再核对原宿主会话桥接，不创建丢失上下文的新会话。
- AC08：修改一段内容后生成新版本；旧版本仍能辨认，新通知不会打开无说明的旧版本。

### 状态和控制

- AC09：运行成功但委托仍需继续时，界面不把整件事标为结束。
- AC10：准备成果与外发失败可以同时显示；失败不隐藏已完成的私有成果。
- AC11：R1 在服务端暂停事务生效后不产生新调度；D0 模拟、R3 实测其与 dispatch_commit 的两种先后。暂停先于 commit 必须阻断；commit 先发生只能显示可能已发生并核实，不以客户端点击时间判断成功。
- AC12：R1 验证 completed、cancelled、expired 后关联触发器停止；归档和取消归档仅改变 archived_at 展示，不重新激活委托。
- AC13：恢复跨过多个计划时间后，只做一次必要的当前检查，不补发历史通知或外发动作。
- AC14：电脑离线时，电脑依赖步骤显示具体原因；不能出现“正在电脑执行”的假状态。
- AC15：移动端离线时缓存有最后更新时间；暂停与撤销显示待同步，不能称服务端已停止；审批与外发不会在重连后自动补交。

### 授权与可靠性

- AC16：私有阅读和范围内成稿不触发外发确认；新增私有资料范围需要相应授权。
- AC17：确认前可看到实际接收者、渠道、完整正文、附件和范围。
- AC18：用户批准后更改接收者或实质正文，再次提交必须校验失败或要求新的授权。
- AC19：R3 对并发撤销进行故障注入：撤销事务先于 dispatch_commit 时零外部派发；reserved 不越过保证边界；commit 后即使尚未发包也不保证取消。只有可证明未传输且已阻止时才显示 cancelled_before_transport；其余核实结果，不假称撤回。D0 使用相同序列模拟。
- AC20：快速双击发送、重传同一请求、重启后重试，外部只产生一次动作；无法保证时不提供真实发送。
- AC21：外部调用超时进入结果待核实，查询结果之前不会自动重复发送。
- AC22：拒绝外发后保留草稿，允许继续阅读和调整，不诱导用户必须开放权限。
- AC23：真实“已完成”状态有对应回执或验证记录；模拟状态全程标识，不混入真实任务列表。

### 记忆和触达

- AC24：用户改稿一句“再短一点”只影响本次内容，不自动成为全局偏好；成果已读用每用户每版本 view receipt 保存，不把 ready 覆写成 viewed。
- AC25：当前任务要求可查看来源、作用域和更新时间；修改后下一次生成使用新要求。
- AC26：删除一条记忆后，新运行和已排队运行不再从主记录、索引、摘要或缓存读取它；原文仍在也不会立即重复提取。
- AC27：项目 A 的要求不会未经选择应用到项目 B。
- AC28：同一结果版本最多一次普通主动通知；用户正在查看时不出现同义推送。
- AC29：没有实质变化的常规检查仅更新详情，不发“已检查”通知。
- AC30：通知关闭或时区未知时，不声称已通知，也不猜测夜间发送。
- AC31：消息中明确约定的时限到达后停止检查，或清楚显示仍未完成并需要新的安排。

### 宿主和可用性

- AC32：D0 核对导航设计；B0 必须真实走通独立工程的侧栏、环境/项目切换、本地会话 ID 和返回路径，并验证重载状态。D1 另在原宿主构建验证桥接与原会话路由。B0 通过不称为原宿主已集成，但不需要等待原宿主代码才能通过。
- AC33：在 375、390、430 CSS 像素宽的交互原型检查空态、长标题、加载、错误、键盘态和半屏表单；原生实现使用对应平台单位另验。
- AC34：主要动作可见且可点，中文长文案不横向溢出，状态不只靠颜色表达。
- AC35：关闭确认面板不会默认批准；退出编辑时明确保存状态；返回不丢失当前稿件。
- AC36：清空演示数据后不残留示例的“已发送”“已连接”或“长期记忆已同步”状态。

## 16 MVP 暂不做

- 默认读取全部历史并形成无法解释的个人画像。
- 从行为推测直接生成全局长期偏好。
- 未经明确授权主动给第三方发消息、发帖、下单或改仓库。
- 新建独立日历、全功能待办中心或审批中心。
- 为所有场景同时建立专用首页。
- 通用“全部允许”开关、复杂企业角色体系和权限仪表盘。
- 依赖通知数量、记忆数量、运行次数的成就或能力展示。
- 无可靠回执的自动重发、无边界的重试和错过任务批量补执行。
- 对尚未实现的云端常驻、跨端同步、真实后台 Agent 作动画式承诺。

## 17 演示范围和实施建议

### 建议的最小演示数据集

一件持续研究委托、三份可追溯资料、两版草稿、三条显式任务要求、一条被撤销的外发动作。所有具体内容可替换，模拟资料和真实公开资料需分清。

### 演示主线

交代 → 明确工作约定 → 准备 → 离开后出现成果 → 直接阅读 → 修改 → 查看这次沿用的要求 → 看到新证据更新 → 外发前确认 → 暂停。

主线之外可从演示控制入口切换四个必要异常：来源失效、电脑离线、授权过期、外部结果未知。演示控制不能混入实际产品普通用户界面。

### D0 约一周的范围控制建议

- 步骤一：对照宿主入口与组件，锁定一个演示场景和状态字典；未接代码的路由标为模拟。
- 步骤二：完成工作简报、模拟对话衔接、成果阅读和版本更新。
- 步骤三：补齐任务内记忆、具体授权、暂停恢复和异常状态演示。
- 步骤四：执行 D0 验收、对照真实宿主截图、修正文案与误导性状态。

以上仅约束 D0，不包含 D1 宿主工程接入，更不包含 R1 后台交付。D1 需拿到宿主代码或桥接并实测；R1 需验证真实服务、调度、持久化和跨日运行。未确认人员、代码与部署条件前不报告这两个阶段的工期。不能为满足演示时限省略状态真实性和权限边界。

### 成效判断

第一轮测试看三件事：用户能否迅速说出“已经准备了什么”；能否无帮助地阅读、修改和暂停；能否分清“草稿可用”“已经发送”“仍在持续跟进”。完成时间、误触和确认次数作为观测数据，不预先宣称提升了多少效率。

## 18 最小待决策项与风险

### 首版默认与必要决策

1. 已确定 iOS 编码与 B0 基础复刻；先按内容研究与私有稿推进，场景保留可替换性，不等待用户重新选择。
2. 原宿主 D1 回接不阻塞独立工程；真实 provider 与 R1 后台必须并行核查并推进，只有费用、新授权或数据处理边界需要用户决定。具体执行里程碑见第 22 节。原约一周建议不是新增 iOS 工程和真实后端的交付承诺。

不需要现在让用户决定数据库、调度框架、每个权限字段或全部通知阈值；这些可由实现者依据现有能力提出收敛方案。

### 关键风险和处理

- 主动性被做成消息轰炸：把“是否值得通知”独立于“是否检查成功”，以有用成果为默认触发。
- 有记忆停留在文案：D0 展示任务要求的来源、复用、修改、删除；R1 实测数据效果和删除传播。
- 审批再次占据产品中心：阅读和准备直接进行，确认只在具体动作上下文出现。
- 能力演示超出后台现实：区分模拟、应用内、云端、电脑执行，每种状态对应可查证事实。
- 持续委托与定时任务重复：一个业务对象、一条归属关系，不在两个入口维护互相独立的规则。
- 后台“完成”缺乏外部证据：通过回执和幂等检查守住已执行状态，未知结果显式保留。
- 首版铺太宽：只接一个场景、一种主要输出和一条可靠执行链，其余以可替换配置说明。
- 语音被误写成全链路免费或离线：设备、提供方与模型分别验收，ASR 和 TTS 分开说明成本、数据处理位置和能力。
- 误识别或外放泄露：保留可编辑转写、明确朗读动作和同一业务确认，敏感新内容不自动读出。

## 19 交付给实现者的冻结建议

可以先据此冻结：现有功能基础复刻是必做范围；一个核心助理场景、一个主成果、复用统一基础组件与数据、四类独立状态、任务内记忆和权限范围分离、带回执的真实完成语义。

暂不冻结：具体技术主题、助理入口在侧栏的最终位置、系统通知默认时段、长期记忆的存储实现、跨端与真实外发接入，以及真实 ASR 提供方、自托管 TTS 部署和最终音色。它们需由实际界面、可用接口或用户最终场景选择决定。

产品验收底线是：用户交代一次后，能在同一件事中看到持续准备和可用成果；任何权限、运行、记忆和执行状态都经得起打开详情核对。

## 20 语音对话与读写

### 20.1 新增范围和产品原则

用户已要求增加语音对话、朗读和口述读写。语音是既有对话与成果的输入输出方式，共用委托、会话、成果版本、权限和执行回执，不建立另一套无法追溯的语音任务。

首版覆盖四个明确动作：

1. 语音交代：口述一件事情，检查转写后提交到当前对话。
2. 连续对话：由用户明确开始前台语音会话，围绕当前事情轮流交流，可随时打断或转回文字。
3. 朗读成果：用户点击朗读当前结果、当前段落或选中文字，能够暂停、继续、停止。
4. 口述改稿：例如“把第二段缩成两句话，保留英文术语”，转写可修改，应用到指定版本并生成新版。

不做常驻偷听、默认唤醒词、自动接听、拨打第三方电话或声纹身份认证。语音不会自动增加连接器、外发、后台录音或长期记忆权限。

### 20.2 放入宿主的方式

- 在既有对话输入区放麦克风入口，不新增语音首页；旁边保留键盘输入。
- 点击麦克风后打开轻量语音面板，明确显示是否正在收音、转写、等待回答或播放。波形只是辅助，不能代替文字状态。
- 语音面板持续显示转写和文本回答，用户不依赖听觉也能检查完整内容。
- 在既有成果阅读器的工具区放“朗读”，并给出当前段落、暂停/继续、停止和语速控制；不会先出现业务授权弹窗。
- 连续对话是用户主动选择的会话模式，界面始终可见“结束语音”；关闭面板或结束语音时停止采集和播放。
- “结束语音”只结束音频会话，不自动结束持续委托。若委托仍在跟进，给一句“语音已结束，这件事仍会按原约定继续”。

### 20.3 四条可测试旅程

语音交代：用户点麦克风 → 看到必要的权限与处理说明 → 说出要求 → 停止或结束本轮 → 获得可编辑转写 → 点击提交 → 沿用原任务理解与范围判断。若原话没有持续意图，语音也不把它变成长期委托。

连续对话：用户主动开始 → 界面显示正在收音 → VAD 判断本轮结束并转写 → 普通低风险对话可按已选模式提交 → 给出文本回答并在本次会话内朗读 → 用户说话或点“打断”停止当前播放 → 下一轮继续。首轮和任何低置信度或关键信息不确定的转写应停在可编辑状态；用户随时可切回“逐条确认转写”。不能以纯静默、背景噪声或含糊附和作为新的业务指令。

朗读成果：用户点“朗读”或明确说“读一下这份草稿” → 选择全文、摘要或选中段落及当前可用输出方式 → 固定成果版本后开始 → 暂停后保留段落位置 → 停止后不自动跳到其他成果。用户选“全文”时不能只读模型摘要；链接、代码和表格的读法应明确、可预测，并保留完整可视文本。后台产生新版时只提示，继续朗读固定旧版并保持旧版正文可视，不自动换页；用户进入编辑，或将当前显示正文切到新版之前，先停止旧版播放。删除、撤下成果或撤销相关权限时立即停止。任何情况下都不能同屏显示新版却继续读旧文。

口述改稿：选择稿件或当前段落 → 说出修改要求 → 查看并修正转写 → 确认目标段落和基于哪个版本 → 生成新版本 → 显示修改点。已有外发批准若绑定旧正文，新版使其失效，不能因通过语音修改而继续使用旧批准。

演示样例：“把刚才草稿的第二段缩成两句话，保留英文术语。”这只是当前研究场景的可替换测试语句，不代表用户要求所有写作长期遵循这一风格。

### 20.4 连续对话 VAD 和打断

- VAD 用于估计说话开始与结束，不判断身份、授权或事实真伪。
- 沉默结束阈值、最长一轮时长和噪声容忍先作为可调参数，不把示例阈值当成所有语言的最终值。用户有清楚的“说完了”或停止按钮。
- 连续对话内支持用户开口打断正在朗读的回答，同时始终保留手动打断按钮；若目标设备无法可靠处理回声与双工收音，先使用按键打断，不伪装已经实现全双工。
- 打断应取消当前输出轮及其尚未播放的音频。迟到的流式片段不能恢复已经停止的声音，多次点击也不能叠加播放。
- 助理自身的 TTS、系统提示音、播放中的视频或通知朗读不能被当作用户确认。回声或来源不明确的识别片段不得提交外发动作。
- “停一下”在语音场景优先停止当前朗读；“停止跟进这件事”才进入已有委托停止逻辑。界面区分暂停朗读、麦克风静音、结束语音、暂停事情四个动作。
- 语音结束不取消已提交的业务动作。若用户要求停止业务，仍以服务端 dispatch_commit 边界报告能否保证阻断。

### 20.5 转写编辑与误识别

单次听写默认先显示可编辑文本再提交。连续对话允许用户明确选择普通对话自动提交，但保留实时转写、立即更正和切换逐条确认的入口。

出现以下情况时，不自动消费识别结果：接收者姓名或账号不明、金额或日期有歧义、否定词不确定、识别语言明显不匹配、正文和用户当前目标冲突、识别为空或只剩附和词。用一个具体问题核实，不让用户重新录完整段落。

用户修改转写时，用户编辑版本与原始 ASR 修订分开；开始编辑后迟到识别结果不能覆盖用户已改字。提交冻结最终正文与版本，以修改后提交的文字作为业务输入；必要时保留“由语音转写，提交前已修改”的普通来源标记，不保存原音来证明用户说过什么。未提交的转写不自动加入长期记忆或正式对话记录。提交后文字按现有对话保存与删除设置处理。

### 20.6 朗读边界与敏感内容

朗读路线已经核实为本地，或已有与处理方、数据类别和用途匹配的传输许可时，普通私有草稿由用户点击即可朗读，不需要额外业务审批。用户明确要求朗读某段，也属于本次用户动作；它不能补足一个身份未知的远程接收方。

涉及敏感内容时，默认先在屏幕提示有需要用户决定是否朗读的部分，由用户明确选择后播放；不能因为进入连续对话，就把新检索到的敏感正文、联系方式、账户信息或外部通知自动读出。系统推送和第三方消息到达时默认只做正常通知，不自动开启扬声器朗读。

TTS 可能涉及把文字传给设备服务或远程提供方。只有已经核实为本地处理的路线才能以“本地朗读”展示；无法核实处理方和位置的 unknown 路线只允许公开或合成测试内容，私人正文和麦克风音频不得进入。任何远程 ASR 或 TTS 在传输前都必须取得与处理方、数据类别、用途和范围匹配的传输许可；麦克风权限不等于云上传许可。未获得适当授权前，不把敏感正文发往新的远程 TTS。朗读用户已经选择的文字不等于允许把整段会话上传给音频服务。

首版语音触发外发时打开同一不可变动作确认视图，核对真实接收者、正文版本、附件、渠道与范围，通过屏幕上的具体发送动作完成必要确认。识别出“好”“可以”“发吧”不单独构成可消费批准。语音识别、声纹或音量不能取代现有账号身份和授权判断。

### 20.7 权限和原音隐私

- 仅在用户首次真正选择说话时请求必要的麦克风权限；朗读本身不要求麦克风。拒绝后保留完整文字功能，给系统设置入口，不反复弹框。系统麦克风授权只允许采集，不替代向 ASR 服务传输的单独许可。
- 开始真实 ASR 前明确处理路线：本地识别，或发送给哪一提供方、为什么需要原音、是否存在保留或训练用途。尚未选定提供方或未核实政策时，不开启真实远程识别。
- 原音默认只在处理当前轮所需的短期内存中存在，成功、取消或失败结束本轮后释放；应用不保存录音文件，不做声纹，不用原音训练。
- 音频、可还原音频的内容和敏感转写不得进入普通日志、崩溃上报或分析埋点；排障默认使用状态码、时长和经最小化的非内容指标。
- “应用默认不留原音”不等于第三方必然不保留。远程提供方的实际保留、训练和区域设置必须另行核实，不能用客户端删除掩盖云端处理。
- ASR 转写与 TTS 文本分别最小化传输；不要把全部记忆、全部成果或其他项目内容一起发送。
- 后续若用户要求保存录音，需明确保存对象、用途、位置和删除方式，不能把默认不留静默改成长期保留。

### 20.8 语言 音色与语速

默认跟随应用语言，并允许用户选择识别语言和朗读语言。中文与英文术语混合是首演必须验证的场景；无法识别时可以切换语言或直接改字，不默认将中文交给仅支持英文的模型。

音色列表只显示实际可用的设备语音或已配置提供方音色。无合适中文音色时说明情况，提供安装受支持语音资源的路径或转回文字，不能展示硬编码但无法播放的选项。

语速提供正常及几个易懂档位，初始建议为 0.75、1、1.25、1.5 倍，作为待实机验证的产品参数。切换语速时保留当前段落，不重复生成业务回答；切换提供方或音色引擎如果改变文字的接收方或处理位置，需要先说明，并在实际传输前取得适当授权；不能因它仍叫“系统音色”就跳过核查。

首版不做声音克隆、名人拟声或未经授权的个性化音色。设备与自托管音色的质量需用同一中文样本比较，不以“全球最好”作为未证实宣传。

### 20.9 音频状态与异常恢复

以下是产品可见状态，由技术契约映射到具体音频会话字段；它们不替代委托与 Run 的状态。

| 情形 | 界面和行为 | 不得发生 |
| --- | --- | --- |
| 等待麦克风权限 | 显示为什么需要；可取消回文字 | 拒绝后不断索要权限 |
| 正在收音 | 常驻文字状态和停止入口 | 面板关闭后继续秘密收音 |
| 正在转写 | 展示本轮进度；已有文字仍可见 | 把未完成片段提前用于外发 |
| 准备回答 | 可继续看文字和取消音频输出 | 显示假波形冒充正在说话 |
| 正在朗读 | 标明当前内容和输出状态 | 多个回答叠加播放 |
| 麦克风静音 | 明确“麦克风已关闭”，仍可听回答 | 将麦克风静音解释为暂停委托 |
| 播放暂停 | 保留当前段落位置，可继续 | 自动跳到下一条外部消息 |
| 设备媒体静音或输出异常 | 提供试播、媒体音量/输出设备提示 | 仅收到合成完成事件就声称用户已听到 |
| 来电或系统音频中断 | 暂停播放和采集，中止当前未提交轮的自动提交；保留文字预览 | 通话结束后自动收音，或迟到识别结果触发业务 |
| 切后台或锁屏 | 首版暂停采集与播放，中止当前未提交轮，显示会话已挂起 | 在后台用迟到 final 自动提交指令 |
| 网络断开 | 有已验证本地路线才可继续；否则回文字并保留可编辑转写 | 自动切到未授权云 ASR/TTS |
| 网络恢复 | 用户点继续后重新检查路线和本轮状态 | 重交已经提交的指令或重发外部动作 |
| 没有检测到语音 | 给重试和键盘入口 | 凭空补写一条用户指令 |
| ASR 失败或低置信度 | 保留已识别部分供修改，说明未提交 | 静默丢掉否定词或猜接收者 |
| TTS 无声音或失败 | 保留全文，给停止、重试/更换可用音色；说明当前未成功播放 | 无限重试或自动改用付费/远程服务 |
| 路由切到蓝牙等设备 | 展示可获得的输出路线提示，允许暂停 | 将未听到误记为业务已完成 |

来电、中断、后台或锁屏必须冻结本轮自动提交资格并取消当前采集/输出。迟到 ASR final 只能丢弃，或在回到前台后作为未提交文本供用户检查，不能自动转为业务输入。恢复后必须由用户明确继续或提交。已经提交的业务委托仍按原约定运行，不因音频会话挂起而伪称暂停。

首版不承诺锁屏或后台连续会话。以后如果需要后台朗读或收音，应作为单独能力按实际平台审核、音频策略和隐私说明验收。

### 20.10 分阶段交付与真实性标签

D0 宿主对齐交互原型：可以模拟语音交代、连续对话、转写纠错、VAD、打断与异常恢复。音频用例必须标出“转写示例”或“语音会话模拟”。如果当前运行设备确实支持已核实本地的系统 TTS，可以用非敏感演示正文增加“设备真实朗读”能力点，单独实测；这仍不证明已接入宿主音频会话或真实 ASR。

B0 独立基础复刻：在独立工程已有语音入口和阅读器中实现语音状态与本地设置，真实设备 TTS 按能力实测，ASR 未接入时继续标模拟。它无需原宿主代码。

D1 原宿主适配集成：未来回接原宿主时重新验证麦克风入口、设备 TTS、音频会话、音量与路线、中断恢复、后台安全暂停和无障碍。ASR 可以继续模拟，但必须标识。只有实际通过选定 ASR 路线处理音频才可称真实识别。

R1 真实有限闭环：在既定研究与私有成果链上，增加一个明确选择并说明处理边界的真实 ASR 路线，可为设备离线或经授权的远程处理。真实语音输入提交到同一任务、回显可编辑文本，并遵循既有持久化与权限规则。连续会话先以稳定轮替或按住说话为基线，免按键 VAD 与全双工回声处理另列能力，不把它们作为已经完成的默认体验。R1 是否包含自托管 TTS，取决于质量、算力与部署验收，不把它当成持续委托必需依赖。

R2 及以后：按需求扩展语种、音色和设备支持。R3 的真实外发验收继续适用语音入口；任何语音演示都不提前解锁 R3。背景收音、声音克隆和第三方通话仍不在当前范围。

### 20.11 免费 TTS 建议与待验证条件

当前建议采用设备 TTS 作为不依赖本产品付费云 TTS 接口的基础路线，并把 Qwen3-TTS 自托管作为中文质量升级候选。免费模型许可或没有额外服务调用费，不等于免费算力、免费托管、所有设备自带中文音色或全平台离线。

设备路线优先枚举真实可用语音。浏览器 localService 字段仅作为本地候选信息，需在目标设备断网实测后才能宣称该组合离线可用；不能从一次桌面测试推断所有手机。[设备语音处理位置说明](https://developer.mozilla.org/en-US/docs/Web/API/SpeechSynthesisVoice/localService)

Qwen3-TTS 官方提供 Apache 2.0 模型与固定音色路径，适合评估中文、自托管控制与较少外部依赖；建议比较 1.7B-CustomVoice 与 0.6B 档位的效果、延迟和资源。首版先使用固定音色，避免把声音克隆授权加入基本需求。这是候选推荐，尚未完成目标设备、中文样本、服务成本与稳定性对比，不能称为已经接入或全球最佳。[Qwen3-TTS 官方项目](https://github.com/QwenLM/Qwen3-TTS)

ASR 独立选型。本地识别可先评估 whisper.cpp 多语 base/small，中文不能用 .en 仅英语模型；真实远程识别提供方及传输路线尚未确定。[whisper.cpp 官方项目](https://github.com/ggml-org/whisper.cpp)

浏览器 SpeechRecognition 不默认等同离线，部分实现会使用远程识别，因此只能在明确说明后作为可选路线，失败时回文字，不静默转传。[浏览器语音识别说明](https://developer.mozilla.org/en-US/docs/Web/API/SpeechRecognition)

最终选型用同一批中文、数字日期、英文术语、长句和停顿样本比较：可懂度、关键字错误、首个可听片段延迟、打断后残留播放、长文稳定性、实际资源与费用、离线表现、许可和数据处理位置。模型宣传延迟不能直接用作应用端到端承诺。

### 20.12 新增语音验收

沿用第 15 节阶段规则。D0 验证界面和 fixture 状态；标为真实设备的条目需要设备实际声音与路由测试；真实 ASR 必须在路线选定和传输获授权后验收。

- VA01：用户从原对话麦克风入口交代事情，转写和提交后文字出现在同一会话；D0 标为模拟，真实 ASR 报告具体路线。
- VA02：单次听写在提交前可编辑；“不要发送”中的否定词、接收者、日期和金额有疑义时不会自动发出业务动作。
- VA03：连续对话由明确开始动作进入，有持续收音指示和结束入口；关闭面板后麦克风采集停止。
- VA04：普通连续对话可按所选模式提交，低置信度或关键目标不明时停在可编辑文本；沉默和单个附和词不会批准外发。
- VA05：路线已核实本地或有匹配传输许可时，朗读普通草稿点击即播放，不新增业务审批；没有已知合规路线时阻断私人正文。用户始终能看到同一份全文。
- VA06：敏感新内容与外部通知不会自动朗读；用户选择某段不导致整段会话被上传。
- VA07：无麦克风权限时仍可朗读与文字输入；权限拒绝只给必要说明，不循环弹窗。
- VA08：设备音色列表来自真实枚举；不可用中文音色不会显示为已经就绪，空列表有文字回退。
- VA09：只有目标设备与指定音色通过断网实际朗读，才显示该组合“离线可用”；仅有 localService 标记不能通过。
- VA10：暂停、继续、停止和语速调整保持正确段落与固定版本；全文不偷换成摘要。后台新版本不自动切走可视旧版，用户进入编辑或切换显示正文前先停旧播放；停止后不自动读下一份成果或外部通知。
- VA11：用户打断、删除正在朗读的成果或撤销该音频处理权限后，当前音频与待播队列停止，迟到片段不复播，连续点击不出现叠音；实机记录停止到最后可听声音的耗时。已传给远程服务的文字按真实回执和保留规则处理，不能假称撤回。
- VA12：播放自身 TTS 和背景声音时，不产生被当成用户批准的转写；双工不可靠时提供按键打断并说明能力。
- VA13：麦克风静音、播放暂停、结束语音和暂停事情分别改变对应状态，不互相冒充完成。
- VA14：来电、音频中断、切后台或锁屏时暂停采集与播放并中止当前未提交轮的自动提交；迟到 final 丢弃或只留未提交预览，不触发业务。回到前台后不自动重新打开麦克风；已提交委托仍按原约定继续。
- VA15：断网后只有已验证的本地路线继续；不可用时保留文字，并且不自动调用未授权远程服务。
- VA16：重连后恢复会话先核对本轮是否已提交，不重复提交指令，不补发外部动作。
- VA17：无语音、识别失败、TTS 超时或无声音都有明确文字状态、停止与回退入口，不仅靠播放回调声称用户听到。
- VA18：中文夹英文术语、数字与日期可核对；切识别语言可纠错，切语速不触发业务答案重生成。
- VA19：口述改稿明确目标稿件和版本，生成新版本并显示差异；旧版本外发批准随正文实质变化失效。
- VA20：语音“发出去”不能绕过既有授权，首版外发在屏幕显示同一 ActionEnvelope 并完成必要确认；语音“停一下”不被错误解释为已撤回外部动作。
- VA21：成功、取消、失败结束本轮后，应用没有持久录音文件，普通日志和崩溃上报不含原音；远程提供方保留政策另行验证，不以客户端结果替代。
- VA22：未提交转写不形成长期记忆；提交文字按原对话规则保存。口述临时写作要求不会自动变成全局偏好。
- VA23：D0 页面可明确区分模拟语音、真实设备朗读和未接入的 ASR；可听到样例声音不被宣传为实时语音对话已完成。
- VA24：免费基础路线失败时不静默切换付费或未知远程服务；任何远程 ASR/TTS 先核对匹配处理方、数据类别和用途的许可，麦克风权限不能替代上传许可。unknown 路线不得接收私人正文或麦克风音频。

### 21.2 证据依据与覆盖矩阵

已读取《真实移动端截图恢复记录》和原图附件索引，来源包含 31 张原 App 截图。下面的 L 编号用于对应原图，具体字段、点击去向和状态以实现者逐图建立的证据覆盖矩阵为准；本章节没有重新检视全部像素，不把页面清单扩写成未被观察的表单或后台行为。

证据使用规则：

- confirmed：截图可直接证明的可见元素，或已记录的实际操作结果。必须同时说明证明的是界面还是行为。
- inferred：为形成可运行本地流程提出的合理实现，来源不足以证明原宿主完全如此。可以在实现说明中记录并推进，不标为原有已验证功能。
- unverified：缺少原图、行为或接口证据。优先继续独立工作；缺失部分明确待核，不猜字段、权限或成功结果。
- 新增助理、记忆和语音增强属于 new，不塞进“原功能已复刻”覆盖率。

矩阵至少包含模块/页面、原图编号、已观察元素、行为证据类型、证据状态、独立路由、数据实体、实现层级、fixture 或真实适配器、验收编号、结果和已知差异。原图覆盖率、已证实流程覆盖率、本地持久化通过率和真实远端接入数量分别报告，不能用“31 图都有页面”代替功能完成。

原图中可见的个人历史标题不用于扩展业务推断，测试数据需脱敏或替换。图片阅读器中的黄色业务页面是被打开的产物，不是应用主视觉。镜像外框、光圈和鼠标不复刻进产品。原界面存在的引用未渲染或宽表截断等问题也不作为复刻目标，应记录修复性差异。

### 21.5 本地数据与 fixture 规则

独立工程需保存自己的环境、项目、会话、消息、任务、文件引用、表单草稿和已证实本地设置。实体使用稳定 ID 与明确归属，页面间引用同一数据，不分别复制一份看起来相同的记录。

- 用户在独立工程创建的内容和预置 fixture 分开；刷新或更新种子数据不能覆盖用户已经修改的本地内容。
- 环境切换只切换对应集合和上下文，不自动搬移原任务、项目或文件；切回后仍能找到原记录。
- 本地保存成功、fixture 请求排队和真实后端成功有不同状态，不用一条“已完成”混写。
- 远端 fixture 经过接口适配器，支持成功、拒绝、超时、未知、离线等确定性分支；页面不能直接写死成功回复来绕过状态机。
- 定时配置可以真实保存和显示下一次计划，也可用测试时钟触发 fixture；应用关闭后的真实调度仍属于 R1，不能由页面中的倒计时推断。
- 本地 ID 不冒充原宿主会话 ID，示例连接不冒充用户真实账号，模拟技能安装不改变系统软件。
- 重置演示数据需要明确范围；不能未经说明清掉用户新建数据。发生存储失败时保留可编辑内容并说明未保存，不能弹假成功。
- 本地持久化不自动意味着加密、跨设备同步或安全备份；实际存储和清理方式按工程方案说明。

### 21.6 基础到助理再到语音的融合路线

优先级按依赖关系安排，不把“先复刻基础”解释为必须等所有远端 API 才能开始助理设计。

第一优先 基础主链：完成证据矩阵、应用外壳和环境/项目归属，再做会话创建与历史、进度、文件树和阅读器。先证明“新建本地会话 → 提交输入 → fixture 进度 → 可读成果 → 返回历史 → 重载仍可打开”。

第二优先 补齐现有模块：定时任务、专家、技能、设置与已证实输入面板各有完整本地主路径和持久化。此时不能只剩“稍后实现”占位。截图未见的行为与远端能力以证据缺口或 fixture 边界记录。

第三优先 新增助理融合：在同一工程添加助理入口、持续委托和工作简报。复用基础会话、任务、项目、定时配置、文件与阅读器，不再维护独立的“助理演示数据岛”。暂停、记忆、批准失效与 unknown 等新增状态沿用前文契约，按本地或远端实现层级标清。

第四优先 语音融合：已有语音入口接可编辑听写和连续对话面板，成果阅读器接朗读，口述改稿写入同一成果版本。可用本地设备 TTS 可提前作为独立能力完成；真实 ASR 和全双工质量继续单独验证，不阻塞其他本地功能。语音编辑期间迟到 ASR 结果不能覆盖用户已改的文字，提交冻结最终文本与版本。

真实接入按能力推进：R1 可在这套独立工程上接自己的受控后端与身份/权限服务，不要求先完成 D1 原宿主回接。D1 在后来取得原源码或桥接时，把已稳定的接口适配到原宿主，验证真实宿主身份、路由和组件。它是可选集成路线，不是 B0 或独立 R1 的前置门槛。

## 22 iOS 实施规格与持续交付

### 22.1 已确定的实施方向

用户已明确要求先理清 Plan、产品功能、设计、验收与规格，然后开发 iOS 版本，继续完成最终 Agent App。当前目标因此包括进入原生编码、构建、运行和验证，不能以 D0 原型或完成文档作为终点。

默认实现为 SwiftUI 独立 iOS 工程，基础复刻、个人助理和语音在同一应用中融合。建议先以 iOS 17 及以上为目标，待实际 Xcode、Simulator 和目标设备核实后校准；这只是可改的实现起点，不代表已验证本机环境或用户设备。最低系统与存储实现调整不能成为停止产品推进的理由。

Plan 与证据矩阵达到足以支持首条主链时立即进入编码。原图未见的小范围行为继续标注，并推进其他已明确工作；不等待所有后台、所有音色和所有权限问题都得到答案。

### 22.2 原生首版功能优先级

- 必须先有的基础：环境/项目归属、会话与历史、进度、文件与阅读器、本地持久化，以及定时任务/专家/技能/设置的已证实主路径。
- 同一版加入的助理：持续委托、一个主成果的工作简报、原会话继续交流、成果版本、任务要求、暂停恢复和具体动作确认。
- 同一版加入的语音：已证实语音入口、可编辑听写、前台轮替对话状态、原生设备朗读、口述改稿、取消与音频中断。真实 ASR 路线需要实际能力和许可，未接时保留清楚的阻塞状态。
- 必须推进的真实 Agent 接入：真实模型与至少一条私有成果工作链、工具执行回执、恢复与取消。不能把模型、工具、存储和调度全部永久留成 fixture。
- 可后续扩展：新供应商、多语种质量档、全双工优化、多人共享、原宿主回接、广泛账号连接与电脑执行。用户已明确的基础复刻和 iOS 编码不再列为“可选以后做”。

### 22.5 可本地实现与 provider 注入边界

原生工程必须有真实本地数据存储和本地操作实现，不把所有动作都包成假 provider：

- 本地直接实现：会话/项目/任务/委托 CRUD、表单校验、资源关联、文件阅读、用户改稿和成果版本、任务要求编辑删除、导航恢复、fixture 管理、设备能力探测。
- 可注入模型 provider：实际模型请求、上下文边界、取消、响应版本与费用信息；fixture 只提供测试输入，不伪装推理。
- 可注入资料/工具 provider：指定公开来源读取、受支持文件处理及外部动作；每项独立说明资料范围、执行权限与回执。
- 可注入调度 provider：本地配置与前台恢复检查可真实实现；稳定云调度需真实服务。测试时钟不等于手机被关闭后仍执行。
- 可注入同步/通知 provider：本地保存、设备本地通知、云同步和远程推送分开，系统权限未获准时不冒充已开通。
- 可注入语音 provider：iOS 系统 TTS、已验证本地或经授权的 ASR，以及未来自托管 TTS；不因统一接口就隐式改变数据去向。
- 可注入原宿主 adapter：未来 D1 才替换身份/文件/路由等原宿主桥接，不影响独立工程先运行。

每个 provider 在界面与诊断中记录未配置、待授权、已连接未核验、可用、故障或仅 fixture，并标明最近验证时间。真实 provider 失败后不能自动切到 fixture 并显示成功，也不能静默切到未知或付费供应方。

### 22.6 不把后台无限留待定

在 M1 至 M2 并行建立一张真实接入清单：能力、拟用提供方/接口、当前可用证据、配置与凭据前置、授权、可用测试环境、负责人、下一步及阻塞原因。每项进入代码接口与可执行测试，不能只写“以后接 API”。

首条真实 Agent 链默认选择内容研究与私有草稿：用户给出资料或限定公开来源 → 实际模型处理 → 调用真实可核验的读取/私有成果工具 → 保存版本与来源 → 用户阅读或朗读 → 修改并再生成。工具产生的文件和版本必须真实存在，测试输入改变时结果不能仍是固定预置文本。

后台持续性单独验收：应用关闭或离线时，若只有设备本地实现，应明确显示“下次打开后继续”，不称持续云端 Agent。要满足原定持续委托承诺，需接通受控持久服务、真实触发与状态恢复，并通过 R1 跨日运行和暂停/撤销测试。此项应有具体工程工作和依赖清单，不自动从首版删除。

如果真实服务因凭据、账号/处理方许可、算力、部署环境或接口不可用而受阻，报告阻塞的具体能力和最小所需条件。继续完成不依赖它的本地功能和适配器测试，但不以“Agent App 已完成”掩盖这个缺口。新费用、持续访问、私密数据新接收方或发布/签名等需用户决定的动作，按原确认边界停在相关动作前，不停止全部工作。

### 22.7 iOS 增量验收

- IA01：M0 后存在实际 SwiftUI 工程和可复现构建步骤，不以 HTML 原型或截图作为 iOS 编码完成证据。
- IA02：在核实可用的 Simulator 构建并启动；构建目标、系统版本和测试设备写入记录。工具链不可用时给出具体错误与可继续的源代码工作，不泛称无法开发。
- IA03：侧栏、返回、半屏选择与全屏阅读在原生导航中可走通；键盘出现后输入与提交可达，关闭面板不丢草稿。
- IA04：用户新建会话、消息、定时配置、任务要求与成果，在终止并重开 App 后仍在；不靠页面内变量假装持久化。
- IA05：IP01–18 每项已证实主要流程有 BF 对应测试与证据；未见字段或未接远端明确列缺口，不能靠统一占位弹窗通过。
- IA06：基础文件树、助理简报和语音改稿使用同一个成果 ID 与版本；改稿后不存在三个互相独立的副本。
- IA07：真实本地操作、真实设备能力、真实远端结果与 fixture 状态能在界面或详情中辨认；真实请求失败不会显示 fixture 成功。
- IA08：iOS 系统 TTS 实测开始、停止、音色与速度、来电/后台恢复；音频合成回调不被当成用户已听到或已批准。
- IA09：真实 ASR 报告处理路线、权限和实测结果；未接 ASR 时语音输入说明未接入，不能把模拟转写称为识别成功。
- IA10：开始编辑转写后，迟到 ASR 不覆盖用户改字；final 提交冻结文本/版本，同一次提交不会重复建立消息或工具动作。
- IA11：至少一个真实模型配合真实本地工具或已授权来源，完成私有成果链；正文与证据由实际本次输入生成，可追溯 provider、运行、文件和验证结果。
- IA12：未接稳定云调度时明确下次打开才继续；接通后通过 R1 跨日、应用关闭、服务重启、暂停与重复事件测试，才能声称离开后持续准备。
- IA13：用户拒绝麦克风/通知或网络不可用时仍可使用本地历史、阅读、改稿和已验证设备能力；不为开通功能自动扩大权限。
- IA14：M6 交付可运行源工程、构建/运行说明、测试结果和能力清单；模拟、阻塞与未执行的真机/后端测试清楚列出，不写全部 Agent 能力已经完成。

### 22.8 可改默认与真正待决策项

可以直接按默认推进：SwiftUI 独立工程、暂定 iOS 17+、本地优先存储、截图对齐的黑灰界面与原导航、内容研究与私有稿首场景、设备 TTS 优先、原音不持久保留、跨任务记忆关闭、一次只接一个真实模型/工具链。默认需记录，后续可改，不需要等用户醒来逐项挑框架。

只有影响授权、费用、数据接收方、部署/发布或确实无法推定的业务选择才需要用户决定。原宿主是否能接入、具体 Xcode 状态、哪条 API 已可用属于工程核查，应先拿证据与可行方案回来。

当前文档与 Plan 是持续实现的依据，下一步必须进入已具备条件的 iOS 编码里程碑。后续只在范围或证据有实质变化时更新规格，不反复打包文档替代开发。
